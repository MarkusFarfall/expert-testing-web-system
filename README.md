# Экспертиза КТПП

Русскоязычная платформа подготовки и тестирования экспертов. Несколько независимых банков вопросов, общий и выборочный режимы, сохранение ответов, таймер, история и разбор ошибок. Администратор управляет банками, импортом, резервными копиями и статистикой. Есть PDF/Excel-экспорт, справочные документы, PWA и отдельный Telegram-бот.

## Текущая архитектура

- **Фронтенд:** Next.js 16 / React 19 / TypeScript / Tailwind 4. `output: "export"` в `next.config.ts`; результат сборки — `out/`.
- **Публикация фронтенда:** GitHub Pages, скрипт `scripts/deploy-pages.sh`. Возможен другой статический хостинг.
- **Текущий API:** Deno, `supabase/functions/portal/index.ts` → `lib/router.ts`, Drizzle и postgres.js. Может запускаться как Edge Function или отдельный Deno-сервис (`local-server.ts`).
- **База:** PostgreSQL, схема — `supabase/migrations/`, подключение API — серверная переменная `DB_URL`.
- **Бот:** Python, только стандартная библиотека; собственная SQLite. Инструкция — `bot/README.md`.

`src/lib/auth.ts`, `store.ts`, `api-handler.ts`, `src/db/`, серверные экспорты и `scripts/acceptance.mjs` остались от прежнего Next.js backend. В текущем App Router нет API route-файлов. **Изменения текущего API вносить в `supabase/functions/portal/lib/`, а не только в старые модули.** Старый сценарий приёмки отключён по умолчанию.

В исходной конфигурации фронтенд использует основной адрес API на VDS и запасное имя того же сервера. Это резервирование адреса, не независимый второй сервер. `scripts/deploy-function.sh` публикует облачную Edge Function; он не описывает весь VDS-деплой. Перед публикацией сверяйте целевую инфраструктуру.

## Данные и сессии

Тесты, вопросы, ответы, снимки попыток, результаты, хеши административных сессий и копии банков хранятся в PostgreSQL. Начатая попытка содержит снимок вопросов: редактирование или замена банка не меняет старые результаты.

Текущий фронтенд хранит случайный `ktpp_visitor_id` и административный токен в localStorage, передавая их через `x-visitor-id` и `x-admin-token`. Это **не HttpOnly-cookie архитектура**. Если storage недоступен, идентификатор сохраняется в памяти вкладки; после закрытия/перезагрузки вкладки такая история может стать недоступной. Пароли в localStorage не сохраняются. Административные сессии действуют 24 часа; в базе хранится хеш токена.

PWA кэширует оболочку, но не ответы API. Полноценная сдача тестов требует сети. API с заголовками сессий и пути `/api/`, `/portal/`, `/test-api/` не кэшируются даже при размещении на том же домене.

## Первый запуск и секреты

Для **уже настроенных** установок вход остаётся прежним.

Для новой установки доступны два способа:

1. Задать сильный `ADMIN_PASSWORD` в окружении **сервера API**; пользователь входит с ним.
2. Задать случайный `ADMIN_SETUP_TOKEN` в окружении API. В `/admin` владелец вводит этот код и создаёт пароль. После настройки код можно удалить из окружения. При отсутствии и пароля, и кода публичная настройка доступа закрыта.

Параллельные запросы первого входа не могут создать несколько административных сессий с разными паролями: только успешная вставка настройки разрешает выдачу сессии. Лимит входов обновляется атомарно в PostgreSQL.

**Не публикуйте `ADMIN_PASSWORD`, `ADMIN_SETUP_TOKEN`, `DB_URL`, Telegram-токены и `bot.env`.** Никогда не используйте `NEXT_PUBLIC_*` для секретов.

### Важное замечание для ранее развёрнутой версии

В прежней версии были опубликованы тестовый пароль и миграция с предустановленным хешем. Литералы удалены из текущих файлов, миграция `20261012183100_admin_password.sql` оставлена под тем же номером без установки пароля.

**Это не меняет уже применённую миграцию, пароль на сервере или историю Git.** Если опубликованный пароль использовался в рабочем окружении, владелец должен отдельно заменить пароль и отозвать активные административные сессии. Не считайте удаление строки из исходников ротацией секрета. Рабочие пароли автоматически не сбрасываются.

На reverse proxy нужно ограничивать размер запросов и принимать `x-forwarded-for` только от доверенного прокси. Дополнительно нужны HTTPS, резервное копирование PostgreSQL, политика обработки персональных данных и организационные правила аттестации.

## Запуск фронтенда

```bash
npm ci
# Настройте NEXT_PUBLIC_API_BASE, NEXT_PUBLIC_API_FALLBACKS, NEXT_PUBLIC_BASE_PATH.
npm run dev
```

- `NEXT_PUBLIC_API_BASE`: абсолютный HTTPS URL API или относительный путь за reverse proxy, например `/portal`.
- `NEXT_PUBLIC_API_FALLBACKS`: резервные URL через запятую; пустая строка отключает fallback.
- `NEXT_PUBLIC_BASE_PATH`: путь публикации фронтенда; на Pages — `/expert-testing-web-system`.

Эти параметры встраиваются **при сборке**. Их изменение требует пересборки. Для продакшена используйте HTTPS.

```bash
npm run build
# Публикуется out/, а не работающий Next.js backend.
```

## Запуск API

Требуется Deno 2 и PostgreSQL. Примените миграции по порядку **к выбранной базе**, предварительно проверив адрес и резервные копии. Для локальной разработки:

```bash
# DB_URL и ADMIN_PASSWORD / ADMIN_SETUP_TOKEN задаются безопасно в окружении.
deno check --node-modules-dir=auto --config supabase/functions/portal/deno.json supabase/functions/portal/index.ts
deno run --node-modules-dir=auto --config supabase/functions/portal/deno.json --allow-env --allow-net supabase/functions/portal/local-server.ts
```

Локальный API слушает порт 8787. Не направляйте локальную разработку и автоматические тесты на рабочую базу.

## Импорт Excel

Первая строка первого листа содержит заголовки с точным регистром:

- вопросы: `Id`, `question`, `blockid`, `numberquestion`;
- ответы: `Id`, `answer`, `question`, `true_answer`, `numberanswer`.

Идентификаторы и номера — положительные целые числа. `true_answer`: `1` — верный вариант; `0`, пусто, `NULL`, `-`, `нет` — неверный. У каждого вопроса минимум два ответа и ровно один правильный. Файлы — до 10 МБ каждый, до 10 000 вопросов и 50 000 ответов. Формулы не поддерживаются. Служебная нумерация очищается; образцы доступны в админке.

Excel разбирается в браузере; текущий API получает нормализованный JSON и повторно проверяет данные. Поле JSON `correct` обязано быть булевым. Импорт атомарно заменяет банк выбранного теста, сохраняет предыдущую копию и не изменяет снимки существующих попыток.

При первом обращении к новой базе создаётся учебный банк: **36 вопросов в 6 блоках**. Он не является утверждённым материалом для аттестации.

## Повторы запросов

Чтение и явно идемпотентные сохранение ответа/завершение попытки могут повторяться. Создание тестов, вход администратора, импорт, восстановление копий и другие изменяющие операции **не повторяются автоматически**, включая переключение на запасной URL. При неопределённом исходе интерфейс предлагает сначала проверить результат операции. Серверные ключи идемпотентности для всех создающих операций — отдельное дальнейшее улучшение.

### Браузер

```bash
npx playwright install --with-deps chromium
npm run build:test
npm run test:ui
```

`build:test` предназначен для POSIX shell и собирает приложение с `/test-api`, без рабочих адресов. `test:ui` запускает отдельный временный сервер на порту 4310 и останавливает его после тестов. Все API-ответы синтетические. Проверяются 320/390/768/1440 px, ошибки и повторы, переключение банков, сохранение, завершение, модальные окна и навигация. Скриншоты — `.artifacts/ui/`.

Для ручного просмотра **тестовой** сборки: `node tests/preview-server.mjs` (порт 3000). Данные живут только в памяти, ни с какой реальной базой сервер не связан. **Не публикуйте тестовую сборку вместо рабочей.** После неё перед деплоем снова выполните обычную сборку с production-параметрами.

### Интеграция API с PostgreSQL

Создайте отдельную локальную базу с именем, оканчивающимся `_test`, и примените все миграции:

```bash
# Пример только для локального стенда. Не подставляйте production URL!
export DB_URL='postgresql://user@127.0.0.1:55432/ktpp_test'
for migration in supabase/migrations/*.sql; do
  psql "$DB_URL" -v ON_ERROR_STOP=1 -f "$migration" || exit 1
done
ALLOW_TEST_DB_WRITES=yes deno run --node-modules-dir=auto \
  --config supabase/functions/portal/deno.json --allow-env --allow-net=127.0.0.1:55432 \
  supabase/functions/portal/tests/integration.ts
```

Сценарий **очищает эту тестовую базу**. Он отказывается работать без подтверждающего флага, с нелокальным хостом или именем без `_test`. Проверяет bootstrap и его конкуренцию, rate limit, импорт, приватность попыток, повторное сохранение/завершение, снимки, копии и отзыв сессии. Старые smoke-сценарии также требуют явного разрешения записи и отдельного `TEST_ADMIN_PASSWORD`.

В `.github/workflows/checks.yml` добавлены раздельные CI-задачи фронтенда/бота и Deno/PostgreSQL. Они не требуют production-секретов и ничего не деплоят. Сам workflow ещё должен быть запущен после публикации изменений в репозитории.
